01

Inconsistent addressability between continuous and discrete update paths in update facade

Important
Why it matters
The generic update(item_id, new_value, update_rule) entrypoint specified in §4.9.4.A takes target as item_id, but the implementation bifurcates target semantics: for continuous updates, target must be an attr_key; for discrete updates, target must be an item_id. Calling update with an attribute key for discrete updates returns ErrorCode::InvalidArgument ('discrete updates are item-addressed'), while calling update with an item_id for continuous updates fails with WrongUpdateRule.
Impact if unaddressed
Callers cannot use a uniform identifier scheme across update rules, and discrete updates on items cannot verify whether the item belongs to a continuous or discrete attribute schema.
Evidence
crates/clio-write/src/update.rs:97,138-171,173-198
Confidence
High

Proposed fix (not yet applied)

Standardize target addressability across both paths; either allow discrete updates to accept attribute keys and look up current open items, or enable items to reference their declared attr_key so caller update_rule can be validated against item attribute schema.

03

Discrete update routing silently discards new_value

Minor
Why it matters
The update facade takes new_value as an argument. In the continuous path, new_value is parsed into float and smoothed via EMA. In the discrete path, new_value is completely ignored and None is passed as replacement_id to invalidate(). While closing the prior item satisfies invalidation without bypassing Phase 100040 admission gates, discarding new_value silently without error or replacement linkage is unexpected.
Impact if unaddressed
Callers passing a new value expecting it to replace the discrete fact will only invalidate the existing fact without creating or linking a replacement.
Evidence
crates/clio-write/src/update.rs:186-195
Confidence
High

Proposed fix (not yet applied)

Document why new_value cannot be admitted directly on the discrete branch without bypassing Phase 100040 admission gates, or accept an optional replacement ID for gated replacement.

04

parse_window treats empty array '[]' as valid rather than falling back to series reconstruction

Minor
Why it matters
In parse_window, '[]' parses successfully as Some(vec![]). If continuous_state.window_json is corrupted with '[]' while continuous_observations has retained history points, observe_continuous_impl uses an empty prior window instead of triggering rebuild_window_from_points, resetting the EMA to cold start.
Impact if unaddressed
A corrupted empty window array causes unnecessary cold-start reset despite available historical observations.
Evidence
crates/clio-store/src/attribute_map.rs:89-105, crates/clio-store/src/sqlite_attribute.rs:204-229, crates/clio-store/src/postgres_attribute.rs:208-230
Confidence
High

Proposed fix (not yet applied)

Update parse_window to return None when the parsed array has zero elements (if window.is_empty() { return None; }), ensuring an empty window row triggers history rebuild from continuous_observations.
