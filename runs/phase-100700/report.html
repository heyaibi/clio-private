01

The machine-readable payload carries no derived marker; only the human text view labels the reason

Important
Why it matters
The phase's own goal sentence says the reason is 'labelled derived everywhere it appears', and its failure-mode table lists 'Reason presented as verified' as a defect to fix by adding the derived label. The label exists in exactly one place: the CLI text line. The MCP and in-process JSON payloads, which are what an agent actually reads, serialize a bare `entity_match: true` sitting next to `entities: [...]`, a value that FR-4 span-verifies at write time. Nothing inside the payload tells the reader which of the two keys is an inference. An agent that trusts the payload can report 'the store confirmed the entity matched the query', which is the exact claim the phase exists to prevent.
Impact if unaddressed
Fidelity risk on the primary consumption path. The human CLI user is protected; a programmatic consumer is not. The phase's Implementation Freedom does permit a boolean flag, so this is a duty to label that was met only in prose, not a wrong implementation.
Evidence
crates/clio-retrieve/src/types.rs:155-165; crates/clio-mcp/src/schema_read_defs.rs:100-101; crates/clio-lib/src/cli_read_render.rs:48; adversary-e2e.out.txt (real binary: "entities":["Grace Hopper"],"entity_match":true).
Confidence
High - verified by reading the serializer, the tool schema, and a real payload.

Proposed fix (not yet applied)

Carry the label in the payload the agent reads: rename the key to `entity_match_derived`, or add a sibling `"derived": true`, or extend the `retrieve` tool description to state that `entity_match` is a derived display-only inference and never a verification result. Any of the three closes the gap without changing the rule, the ranking, or the payload's false-omission behaviour.

Considered and dismissed

  • Substring containment matching a name inside a longer token ('art' in 'restart'). Documented in three places (entity_match.rs:26-33, docs/recall-entity-match.md, phase Known Limitations) and pinned by a test. It is a documented design choice, not a defect.
  • Full Unicode case folding is not used, so 'ß' does not match 'SS'. Verified as a real stdlib limit: str::to_lowercase is the stable mapping and the case-folding API is unstable, so no dependency-free fix exists. Documented and tested.
  • The three clio-mcp test-file edits (ops_tools_tests.rs, read_dedup_tests.rs, read_scores_tests.rs) are outside this phase's behaviour. Not a finding: the earlier blocked attempt requested them as an explicit unblock, the resume notice listed them as existing tree state, they touch no production file, and they harden test doubles rather than weaken assertions.
  • No committed end-to-end test at process level. The E2E evidence is a run-artifact script, but the in-repo CLI test pins the exact rendered line and I reproduced the binary run independently, so nothing is unpinned.
  • `#[serde(default)]` on entity_match is inert because ScoredHit derives only Serialize. It matches the existing convention on entities/consolidated/source_ids, so it is consistency, not error.
  • docs/recall-scope-and-dedup.md:35 still describes the always-present per-hit fields as scores and entities. Still true, since entity_match is omitted when false; updating it would be optional polish.

Strongest aspects

  • The rule lives in one 96-line pure function pair with its normalization and its limits documented in the module header, so there is exactly one place to change the match behaviour.
  • The flag is computed once in the retrieval layer and projected by serde, so JSON and text cannot disagree by construction; the render helper only formats a value it is handed.
  • The payload convention is right: the key is omitted when false, so a non-matching hit keeps exactly the shape it had before the field existed, and a test pins that.
  • The false-positive behaviour of substring matching is documented instead of hidden, with a test that names the consequence ('art' inside 'restart').
  • The decision record explains why display-only was chosen and lists what a future rank-based leg would need, which is what the phase asked for and more than most phases deliver.
