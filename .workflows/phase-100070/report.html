01

Dirty-set race condition drops re-dirtied nodes during concurrent maintenance refresh

Critical
Why it matters
When leaves are attached concurrently with background maintenance refresh, any ancestor marked dirty during an in-flight refresh wave is either cleared despite unsummarized changes or removed from dirty_set while still dirty in memory. In both cases, the node will never be refreshed by subsequent maintenance waves.
Impact if unaddressed
Data loss in ancestor summaries; stale or permanently dirty MemTree state under the primary non-blocking write scenario.
Evidence
crates/clio-write/src/memtree_maint.rs:117-136, 175-201, 230-236: snapshot_dirty clones without draining; enqueue_dirty rejects re-insertions as duplicates; refresh_one unconditionally sets dirty = false; and drain_dirty removes nodes from dirty_set even if generation bumped.
Confidence
High

Proposed fix (not yet applied)

Drain dirty IDs on wave snapshot, compare node.generation before setting dirty = false in refresh_one, and do not remove nodes from dirty_set whose generation counter increased after the wave began.

03

Same-depth parallel refresh spawns unbounded OS threads and fully serializes on coarse-grained forest Mutex

Important
Why it matters
Spawning an OS thread per dirty node at the current level without bounding violates the min(P, num_dirty_at_level) mandate and risks thread starvation or memory exhaustion on wide trees. Furthermore, holding forest.lock() inside refresh_one across the entire child read and summary generation serializes all worker threads, negating parallel speedup.
Impact if unaddressed
Unbounded resource usage and zero actual concurrency during level refresh.
Evidence
crates/clio-write/src/memtree_maint.rs:168-179 spawns unbounded thread::scope workers; line 214 locks forest across the entire execution of refresh_one.
Confidence
High

Proposed fix (not yet applied)

Bound worker concurrency to pool budget P, read child summaries under a brief read lock, and perform string aggregation outside the forest write lock.

06

Internal node interval_end calculation truncates during k-ary split

Minor
Why it matters
During node split, sibling.interval_end is set to last.interval_end. If a non-last child in the partition has a later interval_end, the sibling internal node's interval is truncated, causing time-range queries to omit relevant ancestor nodes.
Impact if unaddressed
Incorrect time-range query filtering in memtree_query.
Evidence
crates/clio-write/src/memtree_attach.rs:209-216 assigns last.interval_end without checking whether earlier children in right_ids have greater interval_end.
Confidence
High

Proposed fix (not yet applied)

Call self.refresh_interval_from_children(&sibling_id) after creating the sibling node in split_upwards.
