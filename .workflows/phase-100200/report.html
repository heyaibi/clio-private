Critical 01

Address these before considering the work done.

01

batch with two canonical_put ops on one key commits two active revisions

Critical
Why it matters
canonical_* promises single-slot semantics: a new put must close the prior revision. Inside `batch`, prior resolution runs at pre-flight before the batch's own creates exist, so the second put cannot see (and therefore cannot close) the first put's row. Both rows land with tx_until NULL.
Impact if unaddressed
Two simultaneously active revisions for the same canonical key. canonical_get returns whichever row `ORDER BY tx_from DESC LIMIT 1` happens to win; when both ops share a timestamp (the default `now` is second-precision) the winner is nondeterministic. Downstream code and audit reconstruction see a slot with no well-defined current value.
Evidence
crates/clio-mcp/src/batch_preflight.rs:138-141 (prior = get_item_by_subject at preflight); crates/clio-mcp/src/batch_preflight.rs:179-193 stages only CloseItem{prior}+CreateItem. Reproduction: `printf` two canonical_put ops (key k1, values v1/v2) into `am mcp stdio --db /tmp/adv-can.db` -> batch returns both COMMITTED; follow-up `stats bank=bk` returned {"items_total":2,"items_active":2}. Both staged rows share tx_from "2026-09-19T19:42:41Z".
Confidence
High

Proposed fix (not yet applied)

Resolve canonical priors at commit time inside the transaction (like triple_add's tx-scoped supersede query), or reject a batch that contains two canonical_put ops for the same (bank,key), or fold same-key puts within a batch so only the last survives.

02

Shared-bank permission gate is bypassable via batch and generic tools

Important
Why it matters
The phase introduces shared_* wrappers plus a deployment permission flag as the 'strict tenant boundary'. The check lives only in shared_args, so any caller can reach the same bank through `store`, `canonical_put`, `triple_add`, or a `batch` op with bank="shared", and can read it via `stats`/`inspect`. The boundary is enforced by tool name, not by bank.
Impact if unaddressed
A deployment that has not enabled the shared surface still accepts writes to and reads from bank `shared`; the documented authorization control does not hold.
Evidence
crates/clio-mcp/src/additive_tools.rs:233-255 (gate only in shared_args); crates/clio-mcp/src/runtime.rs:245-259 (resolve_ctx trusts args.bank). Reproduction with default McpOpenOptions (shared_bank_enabled=false): batch store op bank="shared" -> status COMMITTED; `stats bank=shared` -> 1 item; `shared_store` -> code "forbidden".
Confidence
High

Proposed fix (not yet applied)

Enforce the shared-bank permission at the bank-routing layer (reject bank==SHARED_BANK in resolve_ctx unless enabled), or have batch/preflight reject ops targeting the shared bank when the surface is disabled, rather than gating only the three shared_* entry points.

03

Single-op canonical_put supersession is not atomic

Important
Why it matters
commit_canonical invalidates the prior row and then inserts the new row as two separate store calls with no surrounding transaction. An error after the invalidate leaves the slot with no active value while the caller's admission telemetry already succeeded.
Impact if unaddressed
A transient store failure can silently empty a canonical slot; the new value is lost and the old value is closed. The batch path was deliberately made atomic, which highlights the gap in the single-op path.
Evidence
crates/clio-compliance/src/canonical.rs:72-94: store.invalidate_item(...) then store.create_memory_item(...) then record_audit_event(...), all separate calls.
Confidence
Medium

Proposed fix (not yet applied)

Route the single-op put through the batch executor (canonical_batch_writes already exists) or wrap the close+create+audit in one store transaction.

04

AC-100200-03 evidence overstates a vacuous scratchpad-isolation test

Important
Why it matters
The phase file claims the test 'writes a marker to the pad and confirms retrieve returns no scratchpad row'. The test never examines the retrieve response for the marker; its only isolation assertion reads key "zqxj marker", which was never written (the write used key "leak"). The assertion passes for any implementation, including one that leaked.
Impact if unaddressed
The negative guarantee (T100200-03 / FR-21) has no effective regression test on the retrieve side. A future change that accidentally persisted scratchpad content would not be caught by this test.
Evidence
crates/clio-mcp/src/additive_tools_tests.rs:154-184; the closing assertion is `s.scratchpad.read("default","bank-a",Some("zqxj marker"),...) .is_err()`. Phase file AC-100200-03 row (roadmap/phase-100200...:435).
Confidence
High

Proposed fix (not yet applied)

Assert the retrieve hits contain the stored row but none whose id/content came from the pad, or seed the same marker in a durable row and assert exactly one hit; keep the pad write with a real key and assert it is absent from all hits.

Confidence
Medium
